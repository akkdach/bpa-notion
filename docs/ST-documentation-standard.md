# มาตรฐานเอกสารโครงการ

เอกสารกลางว่าด้วย **ชื่อไฟล์ · โครงสร้าง · เจ้าของ · และเวลาที่ต้องอัปเดต** ของเอกสารทุกฉบับในโครงการ
เขียนให้ใช้ได้กับทุก repo ไม่ผูกกับโปรเจกต์ใดโปรเจกต์หนึ่ง — copy ไฟล์นี้ไปวางที่ `docs/` ของ repo ใหม่ได้ทันที

| | |
|---|---|
| เวอร์ชันเอกสาร | 2026-08-19 |
| ชั้นเอกสาร | C — คนเขียน/คนแก้เท่านั้น |
| เจ้าของ | Tech lead |
| ใช้กับ | ทุก repo ในทีม |

> ปัญหาที่มาตรฐานนี้แก้: เปิด `docs/` แล้วเดาไม่ออกว่าไฟล์ไหนคือของจริง · เอกสารซ้ำกัน 3 ฉบับคนละเวอร์ชัน ·
> โค้ดเปลี่ยนแล้วเอกสารค้างอยู่ที่เดิม · ไม่รู้ว่าใครต้องเป็นคนเซ็น

---

## 1. กฎเดียวที่ต้องจำ

```
<PREFIX>-<slug>.md
```

- `PREFIX` = ตัวพิมพ์ใหญ่ **2 ตัว** จาก [ตารางในข้อ 2](#2-ตาราง-prefix) เท่านั้น — ห้ามคิดเอง
- `slug` = ภาษาอังกฤษ ตัวพิมพ์เล็ก คั่นด้วย `-` (เนื้อในเป็นภาษาไทยได้)
- **ไม่มีเลขลำดับ ไม่มีวันที่ ไม่มีชื่อคน ไม่มี `-v2` `-final` `-latest`**

| ✅ ใช้ได้ | ❌ ใช้ไม่ได้ | เพราะ |
|---|---|---|
| `BP-receive-inbound-job.md` | `01-business-process.md` | เลขลำดับไม่ได้บอกว่าข้างในคือเรื่องอะไร |
| `AS-inbound2026-api.md` | `API-Spec-Final-v3.md` | เวอร์ชันเป็นหน้าที่ของ git ไม่ใช่ของชื่อไฟล์ |
| `AD-clients-in-config.md` | `AD-decision.md` | slug ต้องบอกว่า "ตัดสินใจเรื่องอะไร" |
| `DD-work-order.md` | `dd_work_order.md` | prefix ตัวใหญ่ · คั่นด้วย `-` ไม่ใช่ `_` |

## 2. ตาราง prefix

**ชั้น** บอกว่าใครมีสิทธิ์แตะไฟล์ · **เจ้าของ** คือคนที่ต้องเซ็นก่อน merge

| Prefix | เอกสาร | ชั้น | เจ้าของ |
|---|---|---|---|
| `PR` | **Product Requirement** — ทำไปทำไม ใครใช้ ได้อะไร | C | PO / BA |
| `BP` | **Business Process** — workflow + swimlane + exception path | C | BA + user หน้างาน |
| `CR` | **Change Request** — คำขอเปลี่ยนหลัง baseline | C | PO |
| `GL` | Glossary — ศัพท์ธุรกิจ ไทย↔อังกฤษ↔ชื่อฟิลด์ | C | BA |
| `AD` | Architecture Decision Record — ตัดสินใจอะไร **ทำไม** ทางเลือกอื่นคืออะไร | C | Tech lead |
| `TC` | Test & Acceptance — เกณฑ์ผ่าน, คู่มือทดสอบ | C | QA |
| `RB` | Runbook / Ops — deploy, rollback, incident | C | DevOps |
| `IF` | Infrastructure — env matrix, network, secrets (ชื่อ key เท่านั้น) | C | DevOps |
| `ST` | **Standard** — มาตรฐานกลางของทีม (ไฟล์นี้เอง) | C | Tech lead |
| `AS` | **API Spec** — สัญญารายฟิลด์ทุก endpoint | B | Dev |
| `IC` | Interface Control Document — ต่อ 1 interface กับคู่ค้า 1 ราย | B | Dev + ทีมคู่ค้า |
| `DD` | Data Dictionary — ความหมายรายคอลัมน์ | B | Dev |
| `SQ` | Sequence Diagram — flow ที่ข้าม ≥3 ระบบ | B | Dev |
| `EC` | Error Catalog — code → ความหมาย → ใครแก้ | B | Dev |
| `IN` | Integration Brief — 3rd-party service | B | Dev |
| `AR` | Architecture & System Flow | B | Tech lead |
| `ER` | Entity Relationship Diagram | A | เครื่อง generate |
| `RN` | Release Note / Changelog | A | เครื่อง generate |

### ความหมายของชั้น

| ชั้น | ใครเขียน | กฎ |
|---|---|---|
| **A** | เครื่อง generate | **ห้ามแก้ด้วยมือ** — แก้ที่ต้นทาง (โค้ด/schema/tag) แล้ว generate ใหม่ |
| **B** | AI ร่างได้ **คนเซ็น** | ต้องตรงกับโค้ดจริงเสมอ ถ้าขัดกัน = โค้ดถูก เอกสารผิด ต้องแก้เอกสาร |
| **C** | **คนเขียนเท่านั้น** | AI สรุป/จัดรูปแบบให้ได้ แต่ห้ามแต่งข้อเท็จจริงทางธุรกิจขึ้นเอง |

### อยากเพิ่ม prefix ใหม่?

ห้ามเพิ่มเองในโปรเจกต์ตัวเอง — เสนอแก้ไฟล์นี้ (มาตรฐานกลาง) พร้อมเหตุผลว่าทำไมของเดิม 18 ตัวใส่ไม่ลง
prefix ใหม่ต้อง **ไม่ซ้ำ** และ **ไม่ทับความหมาย** ของตัวที่มีอยู่

## 3. ข้อยกเว้น — 2 ไฟล์ที่ไม่ใส่ prefix

| ไฟล์ | เหตุผล |
|---|---|
| `README.md` | GitHub / IDE เปิดอัตโนมัติจากชื่อนี้ เปลี่ยนแล้วพัง |
| `CLAUDE.md` | AI tool โหลดจากชื่อนี้เท่านั้น เปลี่ยนแล้วไม่ถูกอ่าน |

**นอกจาก 2 ไฟล์นี้ ไม่มีข้อยกเว้นอื่น**

---

## 4. โครงสร้างโฟลเดอร์

```
<repo>/
├─ README.md              ← ติดตั้ง · รัน · ตั้งค่า (คนใหม่อ่านไฟล์นี้ก่อน)
├─ CLAUDE.md              ← กติกาสำหรับ AI: คำสั่งที่ใช้จริง, ข้อห้าม, แผนที่เอกสาร
└─ docs/
   ├─ ST-documentation-standard.md
   ├─ AS-<system>-api.md
   ├─ BP-<process>.md
   ├─ postman/            ← จัดกลุ่มด้วยโฟลเดอร์ได้ ไฟล์ข้างในยังต้องมี prefix
   │  └─ TC-postman-<system>.md
   └─ generated/          ← ชั้น A ทั้งโฟลเดอร์ ห้ามแก้มือ
      └─ ER-<db>.md
```

กติกา:

- เอกสารอยู่ **ใน repo เดียวกับโค้ด** และแก้ **ใน PR เดียวกับโค้ด** — ไม่ใช่ใน chat ไม่ใช่ในไดรฟ์แชร์
- ถ้าที่ทำงานมีระบบ knowledge base ให้ถือว่า repo คือ **ต้นฉบับ** ระบบนั้นคือ **สำเนา**
- โฟลเดอร์ย่อยใช้จัดกลุ่มได้ตามใจ แต่ **ไม่ยกเว้นกฎ prefix**

## 5. โครงหัวเอกสาร

ทุกไฟล์ใน `docs/` เริ่มด้วยรูปแบบนี้

```markdown
---
pmPageId:                              # เว้นว่างได้ ระบบ sync เติมให้เอง
pmParentId:
pmTitle: "[AS] ชื่อที่คนอ่านเข้าใจ"      # [PREFIX] + ชื่อเรื่อง
pmSyncedAt:
---

# ชื่อเรื่อง — คำขยายสั้น ๆ

1–3 บรรทัดว่าเอกสารนี้ตอบคำถามอะไร และ **ใครควรอ่าน**

| | |
|---|---|
| เวอร์ชันเอกสาร | 2026-08-19 |
| ชั้นเอกสาร | B |
| เจ้าของ | Dev |
| แหล่งความจริง | เขียนจากโค้ดจริงใน `src/...` |
```

- `เวอร์ชันเอกสาร` = **วันที่แก้ล่าสุด** รูปแบบ `YYYY-MM-DD` — แก้เนื้อหาเมื่อไหร่ ต้องขยับบรรทัดนี้ทุกครั้ง
- frontmatter ใช้เมื่อ repo ต่อกับระบบ sync เอกสาร ถ้าไม่มีก็ตัดทิ้งได้ แต่ต้องตัดทั้งทีมให้เหมือนกัน

## 6. เขียนอย่างไร

- **1 ไฟล์ = 1 เรื่อง** ยาวเกินไปให้แตกด้วย *ความหมาย* ไม่ใช่ด้วยเลข
  → `BP-receive-inbound-job.md` + `BP-return-work-order.md` (ไม่ใช่ `BP-process-1.md`, `BP-process-2.md`)
- ภาษาไทยเป็นหลัก **ศัพท์เทคนิคคงเป็นอังกฤษ** (endpoint, migration, scope — ไม่ต้องแปล)
- ตารางดีกว่าย่อหน้ายาว · ตัวอย่างจริงดีกว่าคำอธิบาย · สิ่งที่ **ห้ามทำ** ต้องเขียนให้เด่นกว่าสิ่งที่ทำได้
- diagram ใช้ **Mermaid** ในไฟล์ `.md` — ห้าม export เป็นรูปแล้ว commit รูป (แก้ต่อไม่ได้ · diff ไม่เห็น)
- อ้างอิงไฟล์อื่นด้วย **ชื่อไฟล์เต็ม** เช่น "ตาม `BP-receive-inbound-job.md` ข้อ 3"
  ห้ามเขียนว่า "ตามเอกสาร process" — อีก 6 เดือนไม่มีใครรู้ว่าฉบับไหน
- อย่าเขียนสิ่งที่โค้ดบอกอยู่แล้ว (ไล่ชื่อ method, ไล่โครงโฟลเดอร์รายไฟล์) — เขียน **เหตุผล** ที่โค้ดบอกไม่ได้

## 7. ไฟล์ที่เครื่อง generate

ไฟล์ชั้น A ทุกไฟล์ **ยังต้องมี prefix** และบรรทัดแรกต่อจาก frontmatter ต้องเป็น

```markdown
<!-- AUTO-GENERATED — อย่าแก้ด้วยมือ · สร้างจาก: <คำสั่ง/สคริปต์> · เมื่อ: YYYY-MM-DD -->
```

เจอไฟล์แบบนี้แล้วอยากแก้ = ไปแก้ที่ต้นทางแล้วสั่ง generate ใหม่ ห้ามแก้ที่ปลายทาง

## 8. แก้โค้ดตรงไหน ต้องแก้เอกสารตรงไหน

**PR ที่แก้โค้ดโดยไม่แก้เอกสารที่ผูกกัน ถือว่ายังไม่เสร็จ** — reviewer มีสิทธิ์ตีกลับด้วยเหตุผลนี้ข้อเดียว

แต่ละโปรเจกต์ต้องมี **ตาราง traceability** ของตัวเองใน `CLAUDE.md` โดยใช้โครงนี้เป็นตั้งต้น

| แก้อะไร | ต้องอัปเดตด้วย |
|---|---|
| เพิ่ม/แก้ endpoint หรือ field ใน contract | `AS-*` + collection ที่ใช้ยิงทดสอบ |
| แก้ validation rule | ตาราง "บังคับ" ใน `AS-*` |
| แก้กติกาทางธุรกิจ (insert/update/คำนวณ) | `AS-*` + `BP-*` ที่เกี่ยวข้อง |
| เพิ่ม/แก้ scope หรือสิทธิ์ | `AS-*` + ไฟล์ deployment |
| แก้ entity / mapping ชื่อคอลัมน์ | `DD-*` + ตาราง entity ใน `README.md` |
| เพิ่ม config key | `README.md` + ไฟล์ example + ไฟล์ deployment |
| เพิ่ม error code ใหม่ | `EC-*` |
| ตัดสินใจเชิงสถาปัตยกรรม | `AD-*` ฉบับใหม่ — ไม่แก้ทับฉบับเก่า ฉบับเก่ามาร์คว่า superseded |

## 9. ก่อนเปลี่ยนชื่อไฟล์

```bash
grep -rn "<ชื่อไฟล์เดิม>" --include="*.md" --include="*.cs" --include="*.json" .
```

แก้ link ให้ครบทุกจุดก่อน commit — link ตายคือเอกสารตาย

---

## 10. ห้ามใส่ในเอกสาร

- **ค่าจริงของ secret** — connection string, password, app secret, signing key, token, private key
  เขียนได้แค่ **ชื่อ key** และบอกว่าไปเอาค่าจากไหน (user secrets / vault / `.env` ที่ gitignore ไว้)
- ข้อมูลส่วนบุคคลของลูกค้าจริง — ตัวอย่างให้ใช้ข้อมูลสมมติ
- screenshot ที่มี token หรือข้อมูลจริงติดมาด้วย

หลุดไปแล้วให้ถือว่า secret นั้น **ถูกเปิดเผยแล้ว** ต้อง rotate ทันที ไม่ใช่แค่ลบ commit ทิ้ง

## 11. Checklist ก่อนเปิด PR

- [ ] ชื่อไฟล์ตรงรูปแบบ `<PREFIX>-<slug>.md` และ prefix อยู่ในตารางข้อ 2
- [ ] มีหัวเอกสารครบ (ชื่อเรื่อง · เอกสารนี้ตอบอะไร · เวอร์ชันเอกสาร)
- [ ] ขยับ `เวอร์ชันเอกสาร` เป็นวันที่วันนี้แล้ว
- [ ] เช็กตารางข้อ 8 — โค้ดที่แก้ใน PR นี้ ไม่มีเอกสารตัวไหนค้าง
- [ ] ไม่มี secret / ข้อมูลจริงของลูกค้า
- [ ] link ทุกอันกดแล้วไปถึงจริง
- [ ] ชั้น A ไม่ถูกแก้ด้วยมือ · ชั้น C มีเจ้าของตัวจริงเซ็น
